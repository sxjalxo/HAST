# B5 Devices Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Several browsers ("devices") active on one account, each with its own HBSS chain and ML-KEM key, sharing the account's SLH-DSA identity key, linked without a recovery.

**Architecture:** The existing chain becomes device `d1` (the primary chain, which anchors the identity key and is the only one a recovery touches). Every other device has its own chain that starts with a `device` link, cosigned by the identity key. Envelopes are sealed to `name` (d1) and `name#<device>` labels. The server tells which device sent a frame by matching the commitment against the account's active device heads.

**Tech Stack:** Rust (hast-core, axum + rusqlite server, Leptos CSR web), Playwright e2e.

**Spec:** `docs/superpowers/specs/2026-10-28-b5-devices-design.md` (updated: linking uses a typed code, see Task 0).

## Global Constraints

- The user commits; never run `git commit`. Give a one-line message at the end.
- Primary device id is `d1`; other ids are `d` + 8 lowercase hex characters, chosen by the new browser.
- Envelope labels: `name` for d1 (unchanged, so old envelopes still open), `name#<device>` otherwise, lowercase.
- Link payload: `hast-device-v1:<name lowercase>:<device>:<root>:<slh>:<kem>`.
- Link code: 10 characters from `0123456789abcdefghjkmnpqrstvwxyz`, shown `xxxxx-xxxxx`; the offer expires after 10 minutes.
- No new dependencies.

### Task 0: Update the spec (linking by typed code)

**Files:** Modify `docs/superpowers/specs/2026-10-28-b5-devices-design.md`

- [ ] Replace "Linking a new browser" with: existing device makes a random 10-character code, encrypts `{slhSk, slhPk}` under Argon2id(code, random salt) with XChaCha20-Poly1305 (`pq::derive_key`, `pq::encrypt_local`) and posts it as the account's offer; the new browser, signed in, types the code, decrypts, makes its own HBSS and ML-KEM keys, signs its `device` link with both and posts it. Reason: a 6-digit compared code can be ground by a server that substitutes its own transfer key; a typed 50-bit code under Argon2id cannot be guessed offline.
- [ ] Replace the remove-device link with: removal is a server-side flag (`devices.removed_at`). A lost device holds the identity key, so only a recovery cuts it off for sure; say so.

### Task 1: Core device links

**Files:** Modify `crates/hast-core/src/identity.rs`, `crates/hast-core/src/jobs.rs`

**Produces:**
- `LinkKind::Device` (`"device"`)
- `pub const PRIMARY: &str = "d1"`
- `pub fn valid_device(d: &str) -> bool` (`d1`, or `d` + 8 lowercase hex)
- `pub fn device_payload(username, device, root, slh, kem) -> String`
- `pub fn device_link(username, device, kp: &KeyPair, lt: &LongTermKeys) -> ChainLink`
- `pub fn verify_device(username, device, identity_slh, links) -> Result<VerifiedChain, ChainError>`: the first link is a `Device` link HBSS-signed by its root and cosigned by `identity_slh`; the rest go through `extend_chain`; any recovery is `Broken`
- `pub fn extend_device(v, more) -> Result<VerifiedChain, ChainError>`: `extend_chain` with no recoveries
- `pub fn label(username, device) -> String` (`name` for d1, `name#device` otherwise, lowercase)
- `pub fn base_name(label) -> &str`
- jobs: `device_link`, `verify_device`, `extend_device`

- [ ] Tests: accepts a device chain with a rotation; rejects one cosigned by another identity, one with no HBSS signature, one whose payload names another device, a recovery appended to a device chain, and a `Device` link at the start of `verify_chain`.
